# Abada 1.1.0 release notes

**Draft.** Written on `dev` for the 1.1.0 release; it describes what is built and
tested there. It becomes the published notes only when the release owner signs
off the gate ([`1.1-gate-report-2026-10-14.md`](../development/1.1-gate-report-2026-10-14.md))
and the version is bumped. Until then the published release is
[1.1.0-rc.2](1.1.0-rc.2-release-notes.md).

Milestone M4 *Governed improvement and launch* (roadmap
[`docs/development/roadmap.md`](../development/roadmap.md), task specifications
[`m4-task-specs.md`](../development/m4-task-specs.md)). A process can now
improve with people in charge: the Insight loop notices that people overrule an
agent, proposes a small change, shows what that change would have done on real
cases before anyone approves it, and one click returns to the previous version.

REST API v1 and worker protocol v1 stay backward compatible: every change is an
additive field or endpoint, with two intentional behaviour changes listed under
*Behavior changes*. Flyway applies `V34` to `V38`, all additive. Upgrade the
engine, Studio and the agent worker together.

## Signals for reviewed agents (E14)

- An agent may declare `reviewed_by: { node, accept }`: the `human-input` node
  that checks its output and the outcome that keeps it. It changes no routing.
  Deployment checks the node exists, has outcomes, is reachable and that
  `accept` is one of them (`ABADA-APL-REVIEW-001`).
- The engine records, in the transaction that completes the step, each agent
  visit (model, confidence, priced cost) and the reviewer's decision on it
  (`insight_agent_facts`, V34). No payloads, comments or values.
- Insight reports `OVERRIDE_RATE`, `CALIBRATION_GAP`, `CONFIDENCE_DRIFT` and
  `COST_PER_CASE` per agent node, each needing `abada.insight.min-review-samples`
  (20) samples. There are no per-person statistics.

## Replay before approval (E15)

- Replay a proposal on the newest finished cases of the deployment it targets:
  plan (the estimated cost is shown, nothing is spent), start, cancel
  (`/api/v1/projects/{id}/insight/proposals/{id}/replays`). The proposed
  source is walked in memory by the engine's own interpreter, so nothing in the
  running system is touched. Agent steps are one model call each, made by the
  engine; reviewer steps are answered from what the original reviewer decided.
- It is evidence, not a verdict: it shows where the path would have differed.
  **Tools are not run**, reviewer comments are not kept, and a step that needs
  a worker, a timer, a message or a called process stops the case where it
  would wait. Runs are bounded (default 20 cases, at most 100, two at a time)
  and can carry a budget.
- An approval policy can require it: `replayRequired` and `replayMinCases` on
  `PUT .../insight/policies/{key}`. Approvals are then refused with
  `409 REPLAY_REQUIRED` until a finished replay of the proposal's current
  source exists. Studio has a Replay panel on the proposal page, not yet a
  switch for the policy.
- The start variables of root instances are kept so they can be replayed
  (`process_start_inputs`, V36), under the project's evidence policy (absent
  under `none`, masked under `redacted`), encrypted, and cleared after
  retention. **Instances started before this release cannot be replayed.**

## Version history and rollback (E16)

- `GET .../processes/{key}/versions` lists versions with their origin
  (deployed, rolled back, adopted from Insight), deployer and running
  instances; `.../versions/{a}/diff/{b}` returns a source diff;
  `POST .../versions/{v}/rollback` deploys that version's source as the next
  version with a required comment (V35). Running instances stay on the version
  they started on; a rollback whose tools or called processes no longer resolve
  is refused and changes nothing. Studio: *Operations → Versions and rollback*.

## Schema-driven authoring with patch refine (E17)

- The authoring prompt is built from the APL JSON Schema. A refinement is a
  short list of operations the engine applies and validates (`addNode`,
  `removeNode`, `updateNode`, `setEntry`); Insight proposals use it too.
  With no AI model configured, or when no valid change comes back, a refinement
  returns `409` instead of a starter that replaces the process. Re-serialising
  drops YAML comments.

## Bounded for-each (E21)

- `for-each` runs a governed child process per item of a list, at most
  `max_parallel` at a time, with a required `max_items` (V38). Results are
  gathered in item order; an item that fails does not stop the others, and
  `on_error` is taken once after all have settled. See the
  [node reference](../reference/apl-node-reference.md#44b-for-each--for-each).

## Behavior changes

- **A tool name without a server** (`web_search`, the rc.x form) is now refused
  by deployment and validation with `ABADA-APL-TOOL-001`; it was a warning.
  Definitions already deployed keep loading and running unchanged. Replace the
  name with `<server>/<tool>` from a project tool server.
- **Refine without a model** returns `409` rather than a replacement starter.
- A policy-required replay makes `POST .../reviews` with `APPROVE` return
  `409 REPLAY_REQUIRED` until it exists.

## Upgrade

See [Upgrading](../operations/upgrading.md#upgrading-to-110-v34v38-governed-improvement).
All five migrations add tables or nullable/defaulted columns; no row is
rewritten. Back up first and keep `ABADA_ENCRYPTION_KEY` with the backup.

## Rollback

Image rollback does not reverse a Flyway migration. The V34–V38 objects are
ignored by 1.1.0-rc.2, so rolling the engine back without a restore is
possible, with these consequences: replays and for-each items in flight are
not understood by rc.2 (cancel instances waiting at a `for-each` first), and
`reviewed_by` and `for-each` definitions will not deploy there. Restore from
a tested backup when in doubt.

## Known limitations

- A replay does not run tools, called processes, timers or messages, and uses
  one model call per agent step without fallback models.
- Studio draws a `for-each` as a call node and does not edit its loop fields.
- Side effects outside the engine remain at-least-once unless a tool proves an
  idempotency key. Multi-replica claims apply only to the PostgreSQL topology
  covered by the existing concurrency tests.
- Public-cloud certification and an independent security review have not been
  done. BPMN is a documented import subset.
